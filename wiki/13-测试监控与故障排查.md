## 2. 先建立验证层次：每种测试回答不同的问题

《Redis实战篇》经常先展示现象，再分析原因。工程测试也应该先写明期待的业务结果，再挑能验证它的手段。不要因为日志里出现“发送成功”，就结束对完整业务的判断。

| 验证层次 | 使用的对象 | 能回答的问题 | 单独不能回答的问题 |
| --- | --- | --- | --- |
| 静态分层/风格检查 | Java 源文件、ArchUnit 与 Checkstyle 规则 | 是否遵循 Controller → Service → Repository 分层、原生 SQL 参数是否与 @Param 一致、是否符合格式约定 | 真实事务是否成功，消息是否消费 |
| 单元测试 | 一个类与 mock 依赖 | 特定分支会调用什么、是否提前提交 offset、是否误释放锁 | 真实 Redis、Debezium、Kafka 的网络行为 |
| 集成测试 | Spring 与 Testcontainers 启动的 MySQL/Redis/Kafka（CDC 另起 Debezium） | SQL 唯一约束、原生查询能否执行、脚本、多层缓存、真实发送消费、JWT 鉴权 | 长期容量、故障切换与所有生产配置 |
| HTTP/页面测试 | 实际接口和浏览器 | 参数、身份、响应、观察链路是否贯通 | 所有崩溃窗口是否可恢复 |
| 专门故障/性能实验 | 明确负载或故障注入 | 指定条件下的恢复行为、吞吐与尾延迟 | 任何其他规模和所有故障都正确 |

例如“旧缓存回填被拒绝”需要准确控制并发先后；页面随机点几下无法稳定产生这个窗口。相反，“其他用户不能查看订单进度”需要真实 HTTP 身份与归属校验，只 mock 一个 Repository 返回值也不能替代。

<a id="section-02-01"></a>

### 写下预期不变量，再决定怎样测试

不变量是操作前后始终应成立的规则，初学时可理解为“无论重试几次也不能被破坏的底线”。本项目可按下面几条阅读测试：

- 未得到缓存锁的查询不调用回源函数，也不释放别人持有的锁。
- 在途加载经历版本失效后，旧结果不能污染新版本缓存。
- CDC 批次的处理或检查点保存失败时，不提交该批次的 Kafka offset，之后整批重放。
- 同一个行为事件重放不能再次增加统计，同 ID 内容冲突不能伪装成合法重复。
- 本人订单接口必须依据登录身份检查归属，不能只凭订单号给别人查看。
- 对已经履约成功的订单，旧失败消息不能随便归还资格或库存。

每条规则都可以对应一个测试名字和一组断言。这样读测试时关注的是设计为什么成立，而不是只看绿色的数量。

## 3. 用 Testcontainers 隔离运行回归

迁移后不再有单独的测试 Compose。只要本机 Docker 在运行，在项目根目录执行一条命令即可完成 Checkstyle 与全部单元/集成测试：

```bash
# 需要 JDK 21 与正在运行的 Docker；Maven 由项目自带的 Wrapper 下载
./mvnw verify
```

集成测试继承 [IntegrationTestBase](../src/test/java/com/hmdp/support/IntegrationTestBase.java)。它用 Testcontainers 启动 MySQL 8.0（库名 `hmdp_optimization_test`，开启 binlog ROW/FULL）、Redis 7 和 Kafka 3.9.1（镜像 `apache/kafka:3.9.1`），每个 JVM 只启动一次（单例容器），通过 `@ServiceConnection` 把数据源、Redis、Kafka 连接注入所有 Spring 测试上下文；带 `@DirtiesContext` 的测试类只重建 Spring 上下文，不重启容器。容器挂在一个共享网络上，CDC 测试可以再启动 Debezium Connect 容器并按别名访问 MySQL 和 Kafka。

几个容易忽略的细节：

- 测试 JVM 固定为 UTC（`pom.xml` 中 surefire 的 `-Duser.timezone=UTC`），因为容器里 MySQL 的 `NOW()` 是 UTC，否则 `LocalDateTime` 与数据库时间比较会差几个小时。
- 基类带 `@AutoConfigureObservability`，测试中也能读取 Micrometer 指标并对其断言（追踪导出关闭）。
- 需要登录身份的测试用基类的 `accessToken(userId)` / `bearer(userId)` 签发真实 JWT，与 `POST /user/login` 返回的 access token 走同一个 `TokenService`。
- 测试配置显式允许把验证码写日志（`hmdp.mail.log-codes=true`），这样测试能从 Redis 读取验证码而不需要 SMTP；业务环境默认不开。
- 测试库名固定为 `hmdp_optimization_test`，集成测试删除数据前会断言当前库名，不会碰到日常演示库。

第一次运行需要下载镜像与依赖，会比较慢。部分集成测试在自己的配置中开启 MQ/CDC/Kafka，不能仅看 `application.yaml` 默认 `enabled=false` 就认为没有测真实依赖。

## 5. 测试源码导读一：没有拿到锁，必须没有副作用

假设另一个请求正在持有缓存锁。本请求等到边界也没拿到锁，如果错误地执行 unlock，就可能释放别人的保护。测试要同时检查两件事：没有查数据库，没有动别人的锁。

以下为 [CacheConcurrencyTest.java](../src/test/java/com/hmdp/reliability/CacheConcurrencyTest.java) 的相关源码片段。为便于阅读只展示当前部分，依赖与 import 请查看原文件；无需把片段另建类复制运行。

```java
void failedLockAcquisitionDoesNotUnlockSomeoneElse() {
  StringRedisTemplate redis = mock(StringRedisTemplate.class);
  ValueOperations<String, String> values = mock(ValueOperations.class);
  when(redis.opsForValue()).thenReturn(values);
  when(values.setIfAbsent(anyString(), anyString(), eq(10L), eq(TimeUnit.SECONDS)))
      .thenReturn(false);
  CacheClient cache = new CacheClient(redis);
  AtomicInteger loads = new AtomicInteger();
  try {
    assertThrows(
        IllegalStateException.class,
        () ->
            cache.queryWithMutex(
                "test:",
                1L,
                String.class,
                id -> {
                  loads.incrementAndGet();
                  return "value";
                },
                1L,
                TimeUnit.MINUTES));
    assertEquals(0, loads.get());
    verify(redis, never()).delete(anyString());
    verify(redis, never()).execute(any(RedisScript.class), anyList(), any(Object[].class));
  } finally {
    cache.close();
  }
}
```


按准备、执行、断言三段来读：

1. mock 的 `setIfAbsent` 始终返回 false，模拟本请求始终拿不到锁。这里没有启动真实 Redis，所以这是一个分支行为测试。
2. 用 `AtomicInteger` 记录回源函数执行次数；预期 `queryWithMutex` 在等待边界抛出异常。
3. `loads=0` 说明没有绕过锁直接查库。两个 `never()` 分别检查没有 DEL，也没有通过 Lua 执行解锁或回填。
4. `finally` 关闭客户端内部资源，避免测试结束后线程残留。

这个测试只证明“拿不到锁的分支不会回源或误解锁”。旧版本回填、Caffeine 与 Redis 的真实交互要看下面的集成测试，不能把所有缓存保证都归到这个测试名下。

## 6. 测试源码导读二：精确制造旧回填窗口

并发错误难复现，不能只依赖 `sleep` 运气。`CountDownLatch` 是一个可等待的信号：`began` 告诉测试旧加载已经开始，`finish` 让测试控制它什么时候继续。

以下为 [CacheLayersIntegrationTest.java](../src/test/java/com/hmdp/cache/CacheLayersIntegrationTest.java) 的相关源码片段。为便于阅读只展示当前部分，依赖与 import 请查看原文件；无需把片段另建类复制运行。

```java
void concurrentLoadingCoalescesAndInvalidatedFlightCannotPoisonNewGeneration() throws Exception {
  AtomicInteger loads = new AtomicInteger();
  ExecutorService pool = Executors.newFixedThreadPool(8);
  CountDownLatch began = new CountDownLatch(1);
  CountDownLatch finish = new CountDownLatch(1);

  try {
    List<Future<Shop>> reads = new ArrayList<>();
    for (int i = 0; i < 16; i++) {
      reads.add(
          pool.submit(
              () ->
                  cache.queryWithMutex(
                      prefix,
                      1L,
                      Shop.class,
                      id -> {
                        loads.incrementAndGet();
                        try {
                          Thread.sleep(30);
                        } catch (InterruptedException e) {
                          throw new IllegalStateException(e);
                        }
                        return shop("old");
                      },
                      1L,
                      TimeUnit.MINUTES)));
    }
    for (Future<Shop> f : reads) {
      assertEquals("old", f.get(5, TimeUnit.SECONDS).getName());
    }
    assertEquals(1, loads.get());
    cache.invalidate(prefix + 1);
    Future<Shop> old =
        pool.submit(
            () ->
                cache.queryWithMutex(
                    prefix,
                    1L,
                    Shop.class,
                    id -> {
                      began.countDown();
                      try {
                        finish.await(5, TimeUnit.SECONDS);
                      } catch (InterruptedException e) {
                        throw new IllegalStateException(e);
                      }
                      return shop("old");
                    },
                    1L,
                    TimeUnit.MINUTES));
    assertTrue(began.await(3, TimeUnit.SECONDS));
    cache.invalidate(prefix + 1);
    finish.countDown();
    old.get(5, TimeUnit.SECONDS);
    assertNull(redis.opsForValue().get(prefix + 1));
    assertEquals("database", read(cache, loads).getName());
  } finally {
    finish.countDown();
    pool.shutdownNow();
  }
}
```


前半段提交 16 个查询，线程池同时最多运行 8 个。回源函数增加一次计数并短暂停顿，全部请求取得 old，最后 `loads=1` 说明这一轮同 Key 的加载被合并。16 是任务数，8 是工作线程数，不能直接改写成“16 个真实 HTTP 并发”。

后半段先失效，启动一轮新回源并等待 `began`。此时回源已经持有旧版本；主测试线程再次失效，然后用 `finish` 放行，让旧结果有机会尝试回填。这个次序就是人为构造：

```text
加载线程：读版本 → 开始回源 ─── 等待 ─── 返回 old → 尝试回填
测试线程：                收到 began → invalidate → finish 放行
预期：                                            旧回填被拒绝
```

`assertNull(redis...)` 验证旧加载没有重新写 Redis 数据（迁移前这里还有一行检查 Memcache 共享层，随该层删除）。这个测试类继承 IntegrationTestBase，Redis 是 Testcontainers 启动的真实 Redis 7。最后重新读取得 database，确认拒绝旧写没有把后续正确加载永久堵住。

注意，测试并没有断言旧加载线程绝对拿不到 old；它重点保护后续缓存状态。这与“失效一发生，所有已经在途的请求都立即读最新值”不是同一种保证。

## 7. 测试源码导读三：CDC 为什么失败不提交 offset

假设 Debezium 把一批变更写进 Kafka，`DebeziumCacheConsumer` 一次 poll 拿到这一批。投影成功，但还没提交 offset 时出现失败，下次重放应仍能再次处理；如果提前提交，这一批就会被当作已经完成，未执行的缓存失效会留下旧值。

以下为 [DebeziumCacheConsumerTest.java](../src/test/java/com/hmdp/cache/DebeziumCacheConsumerTest.java) 的相关源码片段。为便于阅读只展示当前部分，常量 `UPDATE`、`DDL`、`OTHER_DB` 是三段 Debezium JSON 事件，依赖与 import 请查看原文件；无需把片段另建类复制运行。

```java
@Test
void projectsRowsAndDdlThenCheckpointsBeforeCommitting() {
  DebeziumCacheConsumer consumer = consumer();
  consumer.processBatch(
      List.of(
          record("hmdp-cdc.hmdp.tb_shop", 10, UPDATE),
          record("hmdp-cdc", 3, DDL),
          record("hmdp-cdc.other.tb_shop", 11, OTHER_DB),
          record("hmdp-cdc.hmdp.tb_shop", 12, null)),
      ack);
  ArgumentCaptor<CdcRowChange> change = ArgumentCaptor.forClass(CdcRowChange.class);
  verify(projector).projectRowChange(change.capture());
  assertEquals(CdcRowChange.Operation.UPDATE, change.getValue().operation());
  assertEquals(Map.of("id", "5", "name", "new"), change.getValue().after());
  verify(projector).projectSchemaChange("hmdp", "tb_voucher");
  verify(checkpoints)
      .saveCheckpoint("hmdp-cache-cdc", 10L, "mysql-bin.000003", 4242L, 1700000000000L);
  verify(ack).acknowledge();
}

@Test
void failedProjectionLeavesTheBatchUncommittedForReplay() {
  DebeziumCacheConsumer consumer = consumer();
  doThrow(new IllegalStateException("redis down")).when(projector).projectRowChange(any());
  assertThrows(
      IllegalStateException.class,
      () -> consumer.processBatch(List.of(record("hmdp-cdc.hmdp.tb_shop", 10, UPDATE)), ack));
  verify(ack, never()).acknowledge();
  verify(checkpoints, never()).saveCheckpoint(anyString(), any(), anyString(), any(), any());
  assertEquals(1.0, metrics.get("hmdp.cdc.batches").tag("result", "retry").counter().count());
}
```


第一段一次喂进四条记录，分别是：业务库 tb_shop 的 UPDATE、进入 schema-change topic `hmdp-cdc` 的 DDL、别的库（other）的变更、以及值为 null 的 tombstone。断言说明：

1. 只有业务库的行变更被转换成中立模型 `CdcRowChange`（operation=UPDATE，after 是新值）交给投影器；别的库和 tombstone 被跳过。
2. DDL 走 `projectSchemaChange`，对整张表的缓存命名空间失效。
3. 检查点用消费组名 `hmdp-cache-cdc` 作 destination，batch_id 记 Kafka offset 10，binlog 文件与位置取事件里的 `source.file` / `source.pos`。
4. 最后才调用 `ack.acknowledge()`（容器是 `AckMode.MANUAL`，这一步才提交 offset）。

第二段注入投影失败：要求抛出异常、从不提交、也不写检查点，并且 `hmdp.cdc.batches{result="retry"}` 计数为 1。抛出的异常交给 Spring Kafka 的 `DefaultErrorHandler`，按指数退避（0.5 秒起、最长 10 秒）整批重放，**永不跳过批次**。重放不等于撤销此前已经执行的 Redis 副作用，所以投影器每次都重新读取数据库当前值再失效与回填，重复执行是安全的。

同一文件的 `topicsFollowDebeziumNaming` 还固定了订阅的 topic：三张表的 `hmdp-cdc.hmdp.<table>` 加 schema-change topic `hmdp-cdc`。真实 MySQL → binlog → Debezium → Kafka → Redis 的传播要看 [CacheCdcIntegrationTest](../src/test/java/com/hmdp/cache/CacheCdcIntegrationTest.java)：它用 Testcontainers 启动 `quay.io/debezium/connect:3.7.1.Final` 容器，与 MySQL、Kafka 同网络，验证直接改库后的失效与回填、券迁店时两家店都失效、消费者停止期间的变更在重启后被处理。mock 批次测试不能替代它。

| --- | --- | --- | --- |
| 用户 100 本分钟浏览 | +1 | 100 加入窗口集合 | 无 |

## 12. 监控与链路追踪应看什么

启动 monitoring profile（`docker compose -f dev/docker-compose.yml --profile monitoring up -d`）后，Prometheus（http://127.0.0.1:9091）根据 [prometheus.yml](../dev/monitoring/prometheus.yml) 抓取，告警规则在 [alerts.yml](../dev/monitoring/alerts.yml)，Alertmanager 在 http://127.0.0.1:9094。现在只有一个抓取任务 `hmdp`：用监控凭证（`HMDP_MONITOR_TOKEN`，以 `Authorization: Bearer <token>` 发送）读 Java 的 `/actuator/prometheus`；原来的 canal 抓取任务已删除。监控凭证只授予 ROLE_MONITOR，只能读这一个端点，也不会被当作 JWT 解析。建议结合：

- API 请求量、错误率与延迟，先判断是否影响用户。
- 缓存层命中/回源/被栅栏拒绝的次数，判断查询压力来源。
- CDC 指标：`hmdp.cdc.connected`（分区已分配为 1）、`hmdp.cdc.poll.age.seconds`、`hmdp.cdc.batches{result=success|ignored|retry}`、`hmdp.cdc.rows`、`hmdp.cdc.ddl`、`hmdp.cdc.event.delay`，再结合最近检查点，判断缓存变更是否跟上。
- Stream lag/pending、预约 REVIEW，判断秒杀入口与交接。
- Outbox pending/inflight/review、业务消息发送/消费（指标名仍是 `hmdp.mq.*`，如 `hmdp.mq.client.started`、`hmdp.mq.sends`、`hmdp.mq.consumptions`），判断可靠任务进度。
- Kafka consumer running、lag、浏览 dropped、分析 Outbox，判断统计延迟与丢弃。

Micrometer 源码里的点号名称输出到 Prometheus 时通常转为下划线，计数器还有 `_total` 等后缀。以 `/actuator/prometheus` 的实际输出和告警文件为准。

`/actuator/health` 返回 UP 是基础健康信号，不是 Debezium/Kafka Connect、业务消息或行为分析消费的完整 readiness 证明。体验能力中 connected/clientStarted/consumerRunning 也只是采样状态，必须结合具体任务回执。

当前告警规则：BusinessEventsBacklog、BusinessEventsNeedReview、BusinessEventsSendRetry（Kafka 投递未确认，Outbox 正在退避重试）、BehaviorConsumerStopped、BehaviorConsumerBacklog、BehaviorVisitsDropped、BehaviorEventsNeedReview、DianpingApiDown、CacheCdcDisconnected（CDC 消费分区未分配）、CacheCdcPollingStalled、CacheCdcRetries、CacheCdcDelay、SeckillBacklog、SeckillNeedsReview、SeckillConsumptionSlow、ShopResponseSlow。迁移时删除了 CanalServerDown 和 CacheMemcacheFailure，其余规则的说明文字从 RocketMQ/Canal 改成了 Kafka/CDC。

**链路追踪**：OpenTelemetry Java agent（2.33.1）默认关闭。需要时这样启动，再打开 Jaeger UI（http://127.0.0.1:16686），选择服务 `hmdp-api`：

```bash

```

agent 只挂在 `spring-boot:run` 派生出的应用 JVM 上，不挂在 Maven 进程上。已验证能看到 HTTP、Hibernate/JDBC、Redis、Kafka 生产与消费的 span。注意 Outbox 是异步边界，事件没有透传 traceparent，所以“下单请求”和“稍后 Relay 发送、消费者处理”是两条独立的 trace，不能指望一条链路从 HTTP 一直连到消费完成。

## 13. 从指标读到业务问题：不要只看一个绿色状态

<a id="section-13-01"></a>

### Counter、Gauge、Timer 分别是什么

Counter 是累计次数，通常一直递增。看它是否从 100 变成 101，只能说明又发生一次；判断当前问题强度要看一段时间内的增量或速率。Gauge 是此刻的数量，例如任务积压；Timer 则记录耗时分布。

下面直接解释当前 [alerts.yml](../dev/monitoring/alerts.yml) 中的规则，不要求读者先学完 PromQL：

| 规则中的表达 | 白话含义 | 后续去哪里找原因 |
| --- | --- | --- |
| `max(hmdp_outbox_pending) > 200` | 某实例看到待处理业务任务超过阈值 | `/ops/outbox`、发送错误与依赖状态 |
| `max(hmdp_outbox_review) > 0` | 有任务达到复核状态 | 精确任务 ID、kind、尝试原因 |
| `hmdp_kafka_consumer_running == 0` | 消费线程未处于运行状态 | Java 与 Kafka 日志、功能开关 |
| `max(hmdp_kafka_consumer_lag) > 1000` | 采样到未追上的行为消息超过阈值 | 消费速度、数据库、失败记录 |
| `rate(hmdp_kafka_visits_total{result="dropped"}[5m])` | 最近五分钟浏览丢弃的每秒速率 | 有界队列、发送异常与 Kafka |
| `max(hmdp_cdc_connected) == 0`（且 CDC 已开启） | CDC 消费者没有分配到分区 | Kafka、Connect 状态与消费组重平衡 |
| `hmdp_cdc_poll_age_seconds > 30` | 超过 30 秒没更新轮询时间（空闲事件也会刷新） | CDC 消费线程是否卡住，不等同于某条业务日志延迟 |
| `rate(hmdp_mq_sends_total{result="retry"}[5m])` | 业务事件发送未得到 Kafka 确认、正在退避 | Kafka 状态、Outbox last_error |
| `histogram_quantile(0.95, ...)` | 用直方图估计最近窗口的 P95 | 对应 API 或事件处理的耗时来源 |
| `up{job="hmdp"} == 0` | Prometheus 无法抓到目标 | 接口进程、网络、监控凭证 |

规则还有 `for: 1m/2m` 等持续时间，意味着表达持续成立达到时长才触发。短暂抖动不一定马上告警；看不到告警也不代表完全没有抖动。阈值是当前演示配置，不应直接宣称适合所有生产负载。

<a id="section-13-02"></a>

### 三种“连接正常”仍然可能业务没完成

一是健康接口 UP，但某项后台消费没有开启。二是 Kafka 消费线程 running，却因数据库错误不断回放同一批。三是 Kafka 已确认收到业务事件（Outbox 变为 SENT），但消费尚未完成；或者关单任务还没到期，按设计仍留在 Outbox 里等待。

所以观察顺序应是用户结果 → 任务事实 → 组件指标 → 日志原因。浏览看匹配回执，订单看本人订单与任务状态，缓存看当前读取和失效证据。连接状态用于缩小范围，不能替代完成证据。

## 14. 初学者排障练习：网页有，接口为什么没有数据

```bash

找 web 和 java。`running` 表示容器进程还在，`healthy` 是配置的健康检查结果；都不能独自证明某个业务输入有效。容器刚启动时 Java 可能仍下载依赖或迁移数据库。

| 直接 Java | 代理入口 | 下一步 |
| --- | --- | --- |
| 连接不上 | 同样失败 | 看 Java 启动、端口、依赖 |
| 正常 JSON | 失败或返回 HTML | 看 Nginx /api 转发与地址是否正确 |
| success=false | 同样失败 | 看业务错误与 Java 日志 |

```

## 15. 秒杀排障练习：把一次 PROCESSING 拆成三段

先拿本人接口返回的 orderId，后面所有查询都围绕这个 ID，不在不同请求之间随意切换。分段如下：

```text
尚未完成持久交接？   Stream pending / lag → 预约登记 → Outbox 是否存在
交接后尚未发送？     Outbox state / due / attempts / last_error
已发送尚未履约？     业务消费失败 / Inbox / 预约状态 / 正式订单
```

有 Outbox 且 Stream 已 ACK，不表示请求丢了；恢复责任可能已经交给数据库任务。pending 很多也不必然表示永久失败，可能是处理时间尚未达到接管条件。必须把等待时间、尝试原因和持久事实放在一起看。

管理员只读入口和字段查询示例在 [附录](附录-接口配置与数据字典.md)。确认根因前不要手动 XACK、覆盖库存或直接 UPDATE 预约成功，这些动作会改变恢复证据。需要恢复时，使用现有的按指定对象操作的接口，并复查结果。

<a id="section-15-01"></a>

### 一份故障记录应该保存哪些字段

```text
发生时间与服务版本：
用户看到的现象：
对象 ID（orderId / eventId / voucherId）：
接口的 HTTP 状态和 success：
相关持久状态与 attempts：
组件指标和关键错误：
定位到的窗口：
采取的指定操作：
恢复完成的业务证据：
没有覆盖的剩余风险：
```

这份记录也是面试资料。它能说明你不是随机重启碰巧恢复，而是沿明确的责任交接找到阻塞位置。

## 16. 常见问题速查

| 现象 | 优先检查 | 怎样判断 |
| --- | --- | --- |
| 8080 打不开 | Docker、web 状态、端口占用 | 先 `ps -a`，再 web 日志 |
| 页面在但数据不加载 | Java 是否启动、`/api` 代理 | 直接请求 8081 的公开读接口 |
| Java 启动很慢 | Maven 下载、MySQL 健康、Flyway | 读完整启动日志，不反复删卷 |
| 收不到验证码邮件 | Mailpit 是否运行、`HMDP_MAIL_ENABLED`、SMTP 配置 | 打开 http://127.0.0.1:8025；没有可用 SMTP 时请求直接失败（fail closed），只有显式 `HMDP_LOGIN_CODE_LOG=true` 才写日志 |
| token 存在仍 401 | 请求头、过期、是否已登出 | 请求头必须是 `Authorization: Bearer <accessToken>`；access token 默认 15 分钟过期，前端会先用 refresh token 续期一次；登出后旧 access token 被吊销，refresh token 只能用一次 |
| 登录了却 403/管理失败 | 管理员 ID 与服务环境 | `user/me` 对照 HMDP_ADMIN_IDS（容器内为 CITYLENS_CATALOG_ADMIN_IDS，每次请求实时计算，改后重建 Java 容器即生效） |
| Java 重建后 8080 返回 502 | Nginx 缓存了旧容器 IP | `docker compose -f dev/docker-compose.yml restart web` |
| 429 | 入口窗口、代理 IP 共享 | 等窗口恢复，不循环猛点 |
| 缓存一直无 MySQL 路径 | 已被预热 | 这是命中，不能要求首次必冷读 |
| 体验页提示未启用 | experience flag | 重新创建 Java 才刷新 env |
| 浏览回执不齐 | 有界丢弃、Kafka/消费、数据库 | 按 eventId 刷新，不盲目重发 POST |
| 匿名 UV=0 | 当前 UV 只统计登录用户 | 不等于 PV 也为 0 |
| 秒杀无可领取活动 | 当前时间、状态、库存、发布任务 | 不用过期日期或伪造活动 |
| 订单长期 PROCESSING | Stream/预约/Outbox/Kafka | 沿同一个订单 ID 查持久事实，再看 hmdp-fulfillment 消费组 lag |
| SUCCESS 但未付款 | 预约与订单状态不同 | 看订单 status 与金额快照 |
| 数据库直改页面还是旧值 | Connect 连接器状态、CDC 消费、检查点、版本、TTL | 先 `curl 127.0.0.1:8083/connectors/hmdp-cache/status`，应用更新与直改分别判断 |
| 某张表第一次直改后要等一会儿才失效 | Debezium 首次为该表创建 topic | 消费者要等一次元数据刷新（约 5 秒）和重平衡才订阅上，之后是秒级；不是丢事件 |
| Jaeger 里没有 hmdp-api | `HMDP_TRACING_ENABLED`、observability profile | 两者都开启后重建 Java 容器，再发几次请求 |
| 上传或图片 404 | 上传目录权限、Nginx imgs 挂载 | 文件存在与归属登记分别检查 |
| Flyway 报校验错误 | 修改了已执行迁移 | 核对版本，不盲目清历史表 |

<a id="section-17"></a>

## 17. 秒杀卡住的完整排查顺序

1. 用本人请求状态接口确认 PROCESSING/REVIEW/SUCCESS/FAILED，不先重复创建动作。
2. 管理员查询预约任务、死信，确认 orderId、userId、voucherId 是否一致。
3. 查 Stream pending，判断消息是否尚未交接，是否在等待接管。
4. 查对应 SECKILL_FULFILL Outbox，判断发送失败还是已发送未消费。
5. 检查 Kafka（topic `hmdp.biz.fulfillment`、消费组 `hmdp-fulfillment` 的 lag）、`.DLT` 死信 topic 与错误原因，修复依赖。
6. 对需复核记录执行受控重试；只有明确业务失败才走指定失败与补偿。
7. 重新查订单与对账，不用仅“HTTP 返回成功”判定恢复完成。

`retry` 和 `fail` 都是有业务后果的管理员动作。共享环境先明确影响对象，不批量覆盖未知任务；自己的隔离演示环境可以按测试设计复现。

<a id="section-18"></a>

## 18. 数据恢复的现实边界

MySQL 需要持久卷与备份，Redis 预占依赖 AOF 与存储，Debezium 依赖 binlog 与 Kafka Connect 内部 topic（hmdp_connect_offsets 等）里的位点，Kafka 日志有保留期。Docker named volume 保存不等于具备备份和容灾。

数据库可重建很多投影，但验证码、refresh token、登出吊销记录和签到不是都可重建；Redis 尚未交接的秒杀请求也可能没有数据库事实。不要用全量 `FLUSHALL` 或 `down -v` 当通用排障手段。

告警没有配置外部通知时，只能在本地 UI 观察。准备分享部署时，应补充备份、真实告警通道和维护说明；当前 Wiki 已说明这些边界，不替代实际生产运维建设。

<a id="section-19"></a>

## 19. 可照做的排障方法：建立假设、找证据、验证恢复

<a id="section-19-01"></a>

### 第一步把“不能用”改成一个可观察问题

“项目坏了”无法决定该看哪个组件；“普通用户请求本人订单返回 401”“秒杀预约 30 秒保持 PROCESSING”“浏览 eventId 一直没有事实记录”才是具体问题。记录发生时间、URL、HTTP 状态、业务 success、用户身份范围和对象 ID，先把现象说清。

不要把 access/refresh token、验证码、完整个人信息和数据库密码粘贴到故障报告。需要的是对象关联与状态证据，而不是复制所有请求内容。当前日志只有分秒毫秒，查跨天问题时结合 Docker 日志时间、数据库时间和 sampledAt，避免错对两个不同时间段。

<a id="section-19-02"></a>

### 第二步先读状态，再决定是否重试

| 当前证据 | 可以形成的假设 | 下一步只读核对 |
| --- | --- | --- |
| 直连成功，代理失败 | Nginx 或服务发现异常 | 同一路径两次响应、web 日志、代理配置 |
| 本人接口 401 | 身份未恢复 | `Authorization: Bearer` 格式、access token 是否过期或已登出吊销（`login:revoked:<jti>`）、refresh 是否已被用过 |
| 管理入口 403 | 身份存在但管理配置不匹配 | `/user/me` 的 ID、容器实际管理员配置 |
| Outbox 长期 PENDING | Relay 未领取或未到尝试时刻 | next_attempt_at、调度与开关 |
| Outbox 长期 SENDING | worker 没续租或处理慢 | lease_owner、lease_until、发送错误 |
| 普通事件长期 SENT | 发送成功但消费未持久完成 | 对应消费组、Inbox、消费失败记录 |
| 未到期关单任务 PENDING | 正常等待：Kafka 没有单条延迟消息，任务留在 Outbox，到点才发送 | next_attempt_at、deliver_at 与数据库当前时间 |
| 浏览回执 PENDING | 未落地或尽力采集丢失 | Kafka 运行、失败记录、事实表 |

每个假设都只是下一步调查方向，不是已经确认的根因。例如 PENDING 没有统一含义：普通创建事件 PENDING 很久说明 Relay 没领取或正在退避，关单任务 PENDING 到 deliver_at 则是设计如此，判断依据不同。

<a id="section-19-03"></a>

### 第三步保持同一身份追踪，不靠新增请求冲掉证据

普通订单用 orderId 关联业务 Outbox 与事件历史；Kafka 用原 eventId 查询事实；秒杀用原预约订单号关联准入、预约、履约任务和订单。一个链路里出现多个 ID 时，把映射写进记录，不要随便拿当前最新的一条代替出问题的那条。

频繁刷新店铺可能产生新的浏览事件；重复点击体验采集会生成新 UUID；重新发布活动可能改变原有运行状态。新增成功请求不能证明旧任务已经恢复。排障时先保存原证据，再用只读查询定位责任人。

<a id="section-19-04"></a>

### 四个案例的判断过程

**案例一：首页样式正常，店铺列表为空。**

先看 Network 的分类和 catalog 请求：若根本没发请求，查页面脚本；若返回 HTML，查路径和代理；若 HTTP 200 但 success=false，按 errorMsg 找参数或业务拒绝；若成功且数组为空，再看筛选条件与实际库。静态文件成功不排除后端断开，数组为空也不等于网络坏了。

**案例二：创建订单后页面显示成功，创建事件没完成。**

先看订单是否已存在、Outbox 是否同事务留下。不存在时回到订单事务；存在且 PENDING 时看 Relay；SENT 时看消费；DONE 时看对应事件历史与观察接口是否查错 ID。不要因为后台事件没推进就让用户无依据地取消一个已成功创建的订单。

**案例三：三条浏览事件只有两条 PERSISTED。**

保留三个原 UUID，查询是否同一店铺、同一时间范围。浏览是尽力发送，第三条暂时未落地不自动触发可靠 Outbox 补发。继续看 Kafka 消费、失败记录和采集异常；不能用“提交数 3”作“成功落库数 3”的断言。

**案例四：数据库直改店铺后页面仍旧。**

确认 UPDATE 提交到当前 hmdp 库且是 tb_shop、tb_voucher、tb_seckill_voucher 之一，用 `curl 127.0.0.1:8083/connectors/hmdp-cache/status` 检查连接器与 task 是否 RUNNING，再看 Java CDC 消费状态与 `hmdp.cdc.*` 指标，再核对检查点、缓存失效与短副本时间。若应用写接口正常而直改不传播，优先看 CDC 路径；若两者都不传播，再看共同缓存与查询对象。恢复原店铺名称也应有一轮传播证据。

<a id="section-19-05"></a>

### 第四步做恢复前，先写预期结果

处理前写下“不应该发生的副作用”：重驱动消息不能生成第二份订单，补偿旧预约不能释放新预约，关闭扫描不能覆盖已支付，缓存失效不能清掉签到或 Stream。恢复步骤必须围绕这些规则，并使用已有业务恢复入口。

先确认根因已经去除，再按原身份重试；观察最终事实、任务状态和错误计数是否收敛。只看到接口返回成功不够，例如重试接口可能只重新排队，后续消费仍需要继续检查。

故障注入使用第 3 节的 Testcontainers 集成测试，组件停启和临时数据都在测试自己启动的容器里隔离。日常共享演示不需要为了展示亮点暂停 Broker、删除卷或手动改预约状态；已有隔离测试可以提供相应证据。

<a id="section-19-06"></a>

### 第五步把修复变成一个可重复断言

出现旧回填问题，应把旧加载暂停在明确位置，完成更新失效后再放行，而不是增加随机 sleep 期待撞上。出现重复消息问题，应投递同一身份、比较业务记录与汇总值，而不是仅断言没有抛异常。

异步测试应等待有意义的条件并设置超时，例如原 eventId 事实存在、指定订单状态完成。超时时输出对象状态和任务错误；过短固定等待会让正常慢机器随机失败，过长无界等待会掩盖真正卡住。

<a id="section-19-07"></a>

### 本章的完整故障记录模板

```text
代码版本 / 日期 / 运行模式 / 相关开关：
现象：哪个接口、哪个对象、从何时开始
原始 ID：订单 / 预约 / Outbox / Kafka eventId（按实际填写）
预期不变量：
第一份证据：HTTP 与数据库当前事实
第二份证据：负责下一段的任务、租约、Inbox 或检查点
根因假设 / 已确认根因：
恢复动作及执行身份：
恢复后事实与任务状态：
是否出现额外副作用：
增加或引用的测试与断言：
尚未解释的问题：
```

排障结束的标志是原问题已经收敛、关键不变量未被破坏，并有一份下一位同学可以复核的记录。重启后暂时不报错只是一个观察，还需要说明为什么重启能够继续原任务。
